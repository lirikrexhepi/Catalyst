# Orchestrator (Composer) — Deep Review

**Scope:** every Go package under `internal/`, the `app_*.go` bindings, the desktop React frontend (`frontend/src`), the remote gateway (`internal/remote`) and the mobile PWA (`internal/remote/mobile`).
**Date:** 2026-09-22

## TL;DR — the 12 things holding it back, in order

1. **Your machine is exposed to the internet by default.** On every launch the app starts the remote server on `0.0.0.0:4545` and publishes it via Tailscale Funnel. A 6-digit PIN with no rate limit is enough to log in, and agents run with `--dangerously-skip-permissions` by default. Put together, that's remote code execution by brute force. **[Code]**
2. **Claude permission prompts never work.** The adapter never passes `--permission-prompt-tool stdio`, and its `control_response` has the wrong shape (`request_id` is at the top level instead of inside `response`). The only way Claude agents actually work today is bypass mode. **[SDK]**
3. **Claude's AskUserQuestion reply is broken.** The adapter writes a malformed control response and then a raw non-JSON line to the CLI's stdin. **[SDK][Code]**
4. **Claude doesn't really stream.** There's no `--include-partial-messages`, so text shows up one whole block at a time and never token by token. **[SDK]**
5. **Stop kills a Claude agent for good.** Interrupt kills the process, but the manager keeps the thread registered, so every later message fails with `no active session`. **[Repro]**
6. **Codex/JSON-RPC streaming deltas arrive in the wrong order.** Each notification is handled on its own goroutine. **[Repro]** In the test, 1,976 of 2,000 notifications were handled out of order.
7. **The event bus silently drops events**, including `turn.completed`, whenever a subscriber falls 512 events behind. The card then shows "working" forever and queued messages never go out. **[Repro]**
8. **History stops recording after 20,000 events per thread per run.** User messages and turn ends are silently discarded after that point. **[Repro]**
9. **The feed reducer duplicates, overwrites and loses blocks.** Parallel tool calls leave a "Tool" ghost row and a spinner that never stops. Replaying history loses messages. Diagnostics get overwritten. The coordinator shows a duplicate user bubble on every send. **[Repro]** Harness output is in §7.
10. **Every model switch and resume silently forces bypass mode**, whatever the user chose. **[Code]**
11. **The mobile app drops events and shows duplicates.** It stores only the latest WebSocket message in state, never deduplicates the optimistic user bubble, and shows every Codex/OpenCode message twice (or N times). **[Code]**
12. **Performance: every token re-renders everything.** Each token goes through its own Wails IPC call, then `setTasks` rebuilds every card, and every card keeps 5 tabs plus an SVG-displacement glass panel mounted. There's no batching. **[Code]**

## 1. Security (fix before anything else)

### 1.1 Public remote access is on by default — P0 **[Code]**
- `app.go:169` calls `a.remoteServer.Start(ctx)` unconditionally in `startup`.
- `internal/remote/server.go:88` binds `0.0.0.0:4545`, which is every interface, LAN included.
- `server.go:113` runs `go s.tunnel.StartPublicTunnel(ctx)` automatically. If `tailscale` is installed, it runs `tailscale funnel --bg`, which makes the server reachable from the public internet.
- `auth.go:65-66` accepts the **6-digit PIN** anywhere the 256-bit token is accepted: query string, `Authorization` header and cookie. There's no attempt limit, lockout or delay. That's only 900,000 possible PINs, reachable over HTTPS through Funnel.
- Once authenticated, `/api/agent/send` and `send_coordinator` can drive agents that run with `bypassPermissions` by default (`useOrchestratorStore.ts:73`, `spawner.go:210`). **That is remote code execution.**

**Fix:**
- Make remote access opt-in, and bind to `127.0.0.1` unless the user enables LAN access.
- Never start Funnel automatically.
- Use the PIN only for a one-time pairing step that swaps it for the token. Rate-limit it (for example 5 tries a minute, then lockout) and rotate it after use.
- Make the cookie `HttpOnly; Secure` over Funnel.
- Drop `?token=` from URLs once the cookie is set, so the token doesn't sit in browser history.

### 1.2 Bypass is the default everywhere **[Code]**
- The frontend default is `autoApprovePermissions`, which is true unless explicitly set to `'false'` (`useOrchestratorStore.ts:73`).
- `spawner.go:210`: an empty permission becomes `PermissionBypass`.
- `resume.go:90`, `app_session.go:192` (SwitchTaskProvider) and `app_session.go:305` (UpdateTaskModel) all hard-code `PermissionBypass`. Switching the model on a "safe" agent silently turns it into a `--dangerously-skip-permissions` agent.
- Codex bypass maps to `approvalPolicy: "never"`, but no `sandbox` is ever set.

**Fix:** store the permission mode on `domain.Task` and carry it through spawn, resume, switch and model update.

### 1.3 Claude OAuth token refresh from a third-party client **[Code]**
`internal/claude/refresh.go` uses the Claude CLI's OAuth client id to exchange the user's refresh token, then writes the result back into `~/.claude/.credentials.json`. Your own comment says the rotation race with the CLI can sign the user out, and the lock file only serialises Composer against itself.

The CLI already reports quota in-band through `rate_limit_event`, which you already parse. Prefer that. The SDK also exposes a `get_usage` control request, though the SDK marks it experimental. **[SDK]** Consider removing the refresh path.

## 2. Claude adapter — the biggest parity gap with Claude Code

Everything below was checked against the published Agent SDK, which drives the same CLI over the same stdin/stdout protocol.

### 2.1 Approvals can never reach the UI **[SDK]**
- The SDK adds `--permission-prompt-tool stdio` whenever a `canUseTool` callback is set. Without that flag the CLI makes permission decisions itself and never sends you `can_use_tool` control requests. `buildArgs` never passes it (`claude/adapter.go:69-108`).
- The response shape is also wrong. The SDK writes:
  ```json
  {"type":"control_response","response":{"subtype":"success","request_id":"<id>","response":{"behavior":"allow","updatedInput":{...}}}}
  ```
  Yours puts `request_id` at the **top level** (`adapter.go:296-305`, `schema.go` `ControlResponse`). The CLI matches on `response.request_id`, so your replies are never matched.
- A deny should include `message` (it's required in `PermissionResult`). "Always allow" is currently the same as "once". It should send `updatedPermissions` using the `permission_suggestions` from the request.
- `handleControlRequest` (`translate.go:212`) ignores `request.subtype`. Every control request is turned into an approval card, including `hook_callback`, `mcp_message` and others. Dispatch on subtype instead.

### 2.2 AskUserQuestion **[SDK][Code]**
- Today the adapter intercepts the `tool_use` block and uses the **tool_use id** as a control `request_id`, which is wrong. `RespondToQuestion` then writes that control response plus a **raw, non-JSON line** (`adapter.go:347`) into a stdin that expects stream-json. That line is invalid input to the CLI.
- The correct flow: AskUserQuestion goes through `can_use_tool`. You answer with `behavior:"allow"` and `updatedInput: {questions, answers: {<question text>: <answer>}}`, where multi-select answers are joined with commas (`sdk-tools.d.ts` → `AskUserQuestionInput.answers`).
- The `tool_result` for that tool then arrives with no matching block, and the reducer turns it into a ghost "Tool" row (§7.1).

### 2.3 No token streaming **[SDK]**
- Add `--include-partial-messages` and handle `type:"stream_event"` envelopes (`content_block_delta` → `text_delta` / `thinking_delta` / `input_json_delta`). Emit them with `Delta: true`.
- The SDK typings document the current behaviour exactly: *"the CLI emits one assistant message per completed content block, so several consecutive assistant messages can share `message.id`… `message.usage` is not final."* So you are emitting a `usage` event per block with non-final numbers (`translate.go:122-126`). Your per-turn delta accounting in `usage.go` mostly absorbs this, but ideally you'd read usage only from `result`.

### 2.4 Interrupt, model switch and permission switch don't need a restart **[SDK]**
The comment at `adapter.go:263` ("The CLI has no in-band cancel") is out of date. The SDK sends these control requests on the same stdin:
- `{"subtype":"interrupt"}` — cancels the turn and keeps the process alive, so there's no resume and no cache miss.
- `{"subtype":"set_model","model":…}` — lets `UpdateModel` return `true` instead of forcing stop + `--resume`.
- `{"subtype":"set_permission_mode","mode":…}` — gives you the equivalent of Shift+Tab mode cycling.
- Also available: `get_context_usage` (for a context meter), `rewind_files` (checkpoints) and `initialize` with `systemPrompt` / `appendSystemPrompt`. The initialize route is the right place for your orchestrator `SystemPrompt`, instead of prepending it to the first user message, where compaction eventually drops it.

### 2.5 Other Claude issues
- **Subagents are flattened into the main agent.** **[SDK]** Messages produced inside a `Task` subagent carry `parent_tool_use_id`. `Envelope` doesn't read it, so subagent reads, edits and bash calls are rendered as if the main agent ran them.
- **Resuming with a stale id never falls back.** **[Code]** `StartSession` returns success as soon as the process spawns (`adapter.go:133-178`), so `resumeOne`'s fallback to a fresh session never runs for Claude. The first turn then fails with "no conversation found".
- **Attachments are sent as `@path` text** (`adapter.go:252-255`). Images should go as `image` content blocks (base64) in the user message so they don't depend on @-mention expansion.
- **Parse errors are swallowed** (`readLoop`: `continue`). Log the first N bad lines at least; that's how protocol drift gets noticed.

## 3. Streaming pipeline correctness (backend)

### 3.1 JSON-RPC notifications processed concurrently → reordering **[Repro]**
`internal/jsonrpc/conn.go:118` runs `go c.serve(msg)` for every inbound message, including notifications. In my test, 2,000 ordered `item/agentMessage/delta` notifications came out **1,976 out of order**. For Codex this causes:
- scrambled text deltas;
- `item/completed` overtaking its own deltas;
- `turn/completed` landing before the last tokens, so the card goes idle and text keeps trickling in afterwards.

**Fix:** handle notifications synchronously on the read goroutine, in order. Only requests that can block (approvals) should get their own goroutine.

### 3.2 The bus drops events silently, terminal ones included **[Repro]**
`session/bus.go:36-39` does a non-blocking send into a 512-slot buffer. In the repro, a burst of 3,000 events delivered 512, and `turn.completed` was lost. The desktop subscriber loop in `app.go` does real work per event before pulling the next one: logging, usage, coordinator, constructor, task state, and `runtime.EventsEmit`, which is a synchronous IPC. Codex token bursts can outrun it.

When `turn.completed` is dropped:
- the card stays busy;
- the queue never drains;
- `trackTaskState` never records completion.

**Fix:**
- Never drop control events (`turn.*`, `session.*`, `approval.*`, `question.*`, `tool.*`).
- Coalesce consecutive `Delta` text for the same thread and turn instead of dropping it.
- Or give each subscriber an unbounded ring and apply backpressure only to deltas.

### 3.3 One Wails IPC call per token
`app.go:234` calls `runtime.EventsEmit` for every delta, and each call is a JSON marshal plus a JS eval in WebView2. Batch per thread every 16–33 ms (`agent:events` carrying an array). On the frontend, apply a batch with one `setState`.

### 3.4 Manager memory and transcript growth **[Code]**
- `Manager.history` keeps up to 2,000 events per thread, deltas included. It's never deleted on `Stop`, so it grows for the life of the process. Worse, `SwitchTaskProvider` builds the handoff from this truncated buffer. On a long Codex session, 2,000 token deltas can be just the last couple of turns.
- Store deltas **merged**, keeping one text event per content block, both in memory and on disk (§4).

## 4. Session lifecycle

### 4.1 Interrupt / crash leaves a zombie thread **[Repro]**
Sequence: `Interrupt` → the Claude adapter kills the process → `finish()` deletes the adapter's session and emits `session.stopped` → **nothing reacts to `session.stopped`** (grep shows only the recorder and the mobile UI read it). `Manager.threads` still holds the record, so:
- `HasSession` is `true`, and `ResumeHistory` reports the thread as "live, continued";
- `SendTurn` fails with `no session for thread t1` (repro output: `second Send error = no active session for thread t1`).

The same thing happens when the Claude process crashes or exits on its own, and for Codex when `app-server` dies (`watchExit`).

**Fix:** `Manager.record` should remove the thread when it sees `session.stopped`. Better: have the manager lazily re-start plus `--resume` on the next `Send` when the adapter no longer has the session. That's how Claude Code behaves after Esc.

### 4.2 Orchestrator "message" routing resumes with the wrong id **[Code]**
`constructor.go:316`: `Resume: targetThreadID` passes **your** thread id (`task-3-…`) as the provider session id. The effect by provider:
- Claude: `--resume task-3-…` fails.
- Codex: `thread/resume` fails silently and a new thread starts with no context.
- OpenCode: `GET /session/task-3-…` returns 404, so a new session is created.

The same call also leaves out `Permission`, so the revived agent gets `default`, which is broken for Claude per §2.1. Use `recorder`/meta `Resume[threadID]` and the task's stored permission.

### 4.3 Sending to one history chat resumes the whole workspace **[Code]**
`useSpawner.sendWithModel` → `ResumeHistory(workspaceId)` → `spawner.Resume` starts **every** task in that workspace. Messaging one old chat can launch four CLIs. Resume only the target thread.

### 4.4 Closing a card doesn't close the task **[Code]**
`useSpawner.close` → `StopSession` stops the process, but the task state is never set to `closed`. Only `OrchestratorStopAgent` and `NewChat` do that. Closed cards stay in `FormatAgentManifest` as IDLE/COMPLETED, and the coordinator keeps routing work to them (then §4.2 applies).

The manifest's cwd filter also matches prefixes in **both** directions (`constructor.go` `FormatAgentManifest`). A project at `C:\` or `C:\Users\PC` matches every agent.

### 4.5 Settings changes don't reach running adapters **[Code]**
`Manager.adapters` caches one adapter per driver, and the adapter captures `settings` when it's created. After you change binary path, env or launch args in Settings, new sessions still use the old values until the app restarts.

### 4.6 Early events for new threads are dropped by the frontend **[Code]**
`SpawnTasks` starts the session **and sends turn 1** before it returns. `useSpawner` only calls `threads.current.add(...)` after the promise resolves, and `useSpawner.ts:238` filters out unknown threads. So `turn.started` (which starts the timer) and any fast early deltas are dropped. Register the thread id before sending the first turn, or have the backend return first and send afterwards.

## 5. Orchestrator / coordinator

1. **A user bubble appears twice on every coordinator send.** **[Repro]** `app_coordinator.go:36-38` prepends project memory and the "Active Agents" manifest to `text` *before* `Coordinator.SendWithFiles` records it (`coordinator.go:155`). The echo therefore contains the manifest, the optimistic bubble doesn't, and dedup fails. Reopening history shows the manifest inside the user's bubble. Record the raw user text and send the decorated text.
2. **Phone and desktop fight over the coordinator session.** **[Code]** `remote/server.go:686-702` hard-codes `claude` / `claude-haiku-4-5` / `PermissionPlan`. `Coordinator.matches` compares driver, model, cwd and permission, so alternating between phone and desktop restarts the coordinator each time. Every restart re-primes the system prompt, builds a handoff and stacks another "Switched from…" divider.
3. **Phone-only use can't spawn.** **[Code]** `Constructor.Remember(cfg)` is only called from the desktop path (`app_coordinator.go:41`). If the first coordinator message after launch comes from the phone, `lastCfg` is zero and the plan spawns with `Driver: ""`, which gives `unknown provider`.
4. **Two independent plan executors.** The backend auto-executes plans (`Constructor.Observe`), while the frontend separately parses every coordinator reply (`useCoordinator` → `spawner.inspect`), shows a confirm card, and reconciles through `OrchestratorLatest()`. The frontend also runs `inspect()` on every **worker** turn completion (`useSpawner.ts`, `threadReplies`), so a worker reply containing a `composer:tasks` block pops up a plan card. Pick one owner — the backend — and send `plan` events to the UI.
5. **Cumulative text breaks plan parsing for OpenCode.** OpenCode sends the full cumulative part text on every update. `Constructor.Observe` appends each one with `"\n"`, so the reply becomes N growing copies. The non-greedy regex can then span copies and fail to parse. Key accumulation on part id and replace rather than append.
6. **`mutatingHint` auto-creates worktrees** whenever a prompt contains words like "add", "fix" or "update", without asking. The remote `dispatchPlanTasks` always uses worktrees (`server.go:671`). Make isolation an explicit, per-project setting.
7. **Workers inherit the coordinator's model and options** (`constructor.go` → `SpawnRequest{Driver: cfg.Driver, Model: cfg.Model}`). If the planner is a cheap or fast model, every worker is too. Keep a separate "worker default" model.

## 6. Other providers

### Codex (`internal/codex`)
- **§3.1 reordering** is the main issue.
- **Every message is duplicated on mobile, and the desktop relies on replace semantics.** `item/agentMessage/delta` is emitted with `Delta:true`, then `item/completed` emits the **full** text with `Delta:false` (`inbound.go:113`). The desktop reducer gets away with it by replacing, but only when the last block is still that text (see §7.6). The mobile `mergeEvents` appends it, so every Codex message appears twice.
- **Reasoning:** `textDelta` and `summaryTextDelta` both feed the same thinking block, so raw reasoning and summary interleave. When the reasoning item completes after a message delta, a **second** thinking block is created **[Repro §7.8]**.
- **Live command output only shows the latest chunk.** `outputDelta` is emitted as `tool.result` with `Delta:true`, but `mergeToolBlock` does `output: tool.output || existing.output`, so each chunk replaces the last instead of appending.
- **Approval policy values.** `approvalPolicy(PermissionPlan)` returns `"always"` (`adapter.go:229`), which isn't a Codex approval policy in any version I know (`untrusted` / `on-failure` / `on-request` / `never`). The camelCase spellings `onRequest` / `onFailure` should also be checked against your app-server's schema. **[Unverified]**
- **Approvals never time out.** `onApprovalRequest` blocks on `context.Background()`, so an unanswered approval outlives an interrupt or a stop.

### OpenCode (`internal/opencode`)
- **One `opencode serve` per cwd, never stopped until app exit.** Every worktree adds a resident server. `ensureServer` also returns the cached client even after that server has crashed; check `proc.Done()`.
- **Cumulative, non-delta text with no part id** in the event. The UI can't tell which block to replace, which causes stacking on mobile and relies on replace-if-last on desktop. Add `PartID` to `RuntimeEvent`, or diff against the last text per part and emit real deltas.
- **Every tool state update is a separate event.** Fine on desktop (merged by id); on mobile each update renders another output box.
- `--print-logs --log-level=DEBUG` plus logging every line: a lot of I/O on hot paths.
- The user-echo filter (prefix match against `lastUserText`) can swallow a legitimate reply that starts with the prompt text.

## 7. Desktop UI — stacking, dedup and ordering

I ran `eventReducer.ts` headless with esbuild and node. These are real outputs.

### 7.1 Parallel tool calls leave a ghost row and a spinner that never stops **[Repro]**
Claude usually emits several `tool_use` blocks before any result arrives.
```
## Parallel Bash calls (Claude emits both tool_use before any result)
  tool_group "Worked" items=[["Ran","npm test","running"],["Ran","npm run lint","completed"],["Tool","","completed"]]
```
The cause is in `upsertTool`. When a standalone `tool_bash` or `tool_search` is merged into a new group, the previous item gets **no `id`** and its tool id is **not** added to `memberIds` (`eventReducer.ts:510-551`). Its result can't find the item, so it falls through to `toToolBlock` with no name and becomes a generic "Tool" row. The original stays `running` forever. The same thing happens to any result whose call was dropped (§3.2) or intercepted (AskUserQuestion, §2.2).

**Fix:** always carry `id` and `memberIds` when merging, and **never create a block from a `tool.result` with no matching call**. Buffer it or drop it.

### 7.2 Replaying history loses messages **[Repro]**
```
## History replay: user says "yes" twice
  user "yes"
  text id=text-8 content="Done step 2"          ← "Done step 1" and the second "yes" are gone
```
Two bugs combine here:
- `appendUserMessage` merges any user event whose text matches a user block within the **last 8 blocks** (`:377`). On replay there are no optimistic blocks, so the second "yes" merges into the first.
- `appendText` then **replaces** the previous turn's text because the last block is `text` and `delta` is false (`:428-436`).

**Fix:**
- Deduplicate only against *optimistic* blocks, flagged `pending: true` and matched by a client-generated `turnId` that you pass to `SendTurn` and echo back.
- Only merge text into a block from the **same turn and the same content block**, which needs a stable `blockId` or `partId` from the backend.

### 7.3 A diagnostic or error gets overwritten by the next text **[Repro]**
```
## Diagnostic followed by agent text
  text id=diagnostic-5 content="Here is the answer"   ← the warning is gone
```
Diagnostic and error blocks are `type:'text'`, so `appendText` merges into them. Give them their own block type.

### 7.4 Answering a second question rewrites the first **[Repro]**
```
  question question-q1 answered=true selected="drizzle"   ← was "pg"
  question question-q2 answered=true selected="drizzle"
```
The Claude and OpenCode `question.answered` events carry no `Question.RequestID`, so `resolveQuestion` (`:306`) resolves **all** question blocks. Include the request id in the event (backend) and ignore answered events without one (frontend).

### 7.5 Todo lists stack **[Repro]**
Each `TodoWrite` call creates a new `tool_todo` block, and the Codex `plan` event replaces whichever todo block it finds *first* (`upsertPlan`, `:826`). Claude Code shows one live list. Keep a single `session-tasklist` block, update it in place, and show a compact "Updated tasks (3/5)" row in the feed instead of the whole list each time.

### 7.6 Edits disappear into "Worked" groups **[Repro]**
```
## Read then Edit
  tool_group "Worked" items=[["Read","a.ts","running"],["Edit","a.ts","running"]]
```
If anything tool-like comes before it, an Edit or Write is folded into the group as a one-line row and its diff is gone. The same Edit shows as a full diff card or as a single row depending on what came before. Never fold edits (or todos and questions) into groups.

### 7.7 Thinking never finishes until the turn ends **[Code]**
`closeStreaming` only closes `text` blocks. A thinking block stays `isThinking` through every later tool call and message, so the "Thinking" shimmer and header are wrong for the whole turn. Close thinking when any other block type is appended.

### 7.8 Duplicate thinking blocks for Codex **[Repro]**
A completed reasoning item that arrives after a message delta creates a second thinking block (§6).

### 7.9 Render and performance **[Code]**
- **Every token re-renders everything.** Each event runs `setTasks(prev => prev.map(...reduceEvent...))` **and** `setBackgroundTasks(...)` (`useSpawner.ts:237+`). `reduceEvent` copies the blocks array for each event, `Scene` re-renders, and every `AgentWindow` renders `AgentSessionFeed`. That component re-runs `extractPlanFromText` over **every** text block on every change (`AgentSessionFeed.tsx` `latestPlanBlockId` and inline in `map`).
- **Every card is fully mounted.** Chat, tasklist, browser (with an iframe), servers and changes are all mounted and hidden with opacity (`AgentWindow.tsx`), and every card in the deck renders its full feed.
- **Listeners and callbacks churn.** `useSpawner` returns a new object literal each render, so `useEffect(..., [spawner])` in `Scene.tsx:151-160` **unsubscribes and resubscribes** the `orchestrator:spawned` listener on every token. `handleSubmit`, `handleOpenHistory` and the queue effect also change identity every render.
- **The glass panels are expensive.** `LiquidGlass`/`RefractiveGlass` use SVG `feDisplacementMap` backdrop filters on every card and repaint whenever the feed scrolls underneath.
- **Background polling.** `useServers` polls every 4 s (`POLL_MS`) and each poll starts **PowerShell** twice (`Get-NetTCPConnection` + `Get-CimInstance Win32_Process`). That's constant CPU even when idle.

**Fix, in order:**
1. Batch events (§3.3).
2. Move blocks into a per-thread store (zustand with a selector per thread) so one card's tokens don't re-render the others.
3. Memoise feeds per block (`React.memo` keyed by block identity).
4. Mount only the active tab and skip rendering feeds for cards more than one position off-center.
5. Virtualise long feeds.

### 7.10 Other UI behaviour
- **One dev server shows on every card.** `getTaskServers` falls back to *any* running web server when attribution fails (`Scene.tsx:272`).
- **Queued messages are rewritten before sending.** They're sent as `[Queued Task]: … Instruction: Before taking any action, first record this item into your todo…` (`Scene.tsx:572, 658`). The user's words are changed, the agent is steered, and the bubble shows the wrapper text.
- **Queued messages fire on Stop.** The queue sends on any busy→idle transition, including the user pressing Stop. For Claude that send then fails (§4.1).
- **Two "completed" notifications.** Island notifications fire both for `onBackgroundComplete` and for every busy→idle transition.
- **No Esc-to-interrupt.** In the omnibar, Escape only closes pickers.
- **No slash commands, no `@file` autocomplete, no permission-mode toggle, no context-usage meter.** See §10.

## 8. Mobile app (`internal/remote/mobile`)

1. **Events are dropped.** **[Code]** `ws.ts:41` keeps only the *latest* message in state: `setLastMessage(msg)`. Consumers read it in `useEffect([wsLastMessage])`. With React 18 automatic batching, two frames that arrive before a render collapse into one, and the earlier one is lost. Keep an event queue in a ref and flush it in one `setEvents`, or subscribe consumers directly to the socket.
2. **Your own messages appear twice.** **[Code]** The optimistic `user.message` uses `seq: Date.now()`, and the server echo has the bus `seq`. `mergeEvents` deduplicates by seq only, and `collapseFeed` doesn't deduplicate at all.
3. **Codex messages appear twice and OpenCode messages N times.** **[Code]** `mergeEvents` merges deltas and then *appends* the final non-delta event. Each OpenCode part or tool update becomes another bubble or output box.
4. **Tool calls and results render as separate unrelated rows.** There's no pairing by `tool.id`, so parallel calls read as a jumble.
5. **"Rate limited — waiting" appears on every `rate.limit` event** (`ChatBubble.tsx`). Claude sends these frames as normal quota status, not only when you're throttled.
6. **The running badge never shows.** **[Code]** The server sends `runningAgents` (`server.go:318`), while the client reads `runningCount` (`types.ts:94`, `Drawer.tsx:126-129`).
7. **Heavy polling.** `/api/projects` is polled every 4 s. Each call copies `manager.History()` (up to 2,000 events) for every agent to compute `LastActivity`.
8. **Dead agents stay dead.** A send to an ended agent returns `session_ended` with no resume path; the desktop at least calls `ResumeHistory`. After §4.1 this path is hit constantly.
9. **Messages can be sent twice.** When the HTTP call fails, `handleSend` retries over WebSocket. If the HTTP request actually reached the server, the message goes twice.
10. **Two separate rendering pipelines.** `mergeEvents`/`ChatBubble` duplicates the logic of the desktop `eventReducer`, and every fix has to be made twice. Put one reducer in a shared TypeScript package, or better, reduce on the backend and send **blocks** (see the architecture note below).
11. **The remote server can hang on Stop.** `broadcastEvents` writes with no deadline while holding `s.mu.RLock`. One stuck phone blocks `Stop()`, which needs the write lock. Set `SetWriteDeadline` and give each client its own writer goroutine.
12. **Build coupling.** `internal/remote/web/index.html` is dead (only `mobile/dist` is embedded), and `//go:embed all:mobile/dist` means a clean checkout won't compile until the mobile app is built.

## 9. History and persistence

- **The 20,000-event cap silently drops data.** **[Repro]** `store.go:289`. The counter is in memory, so the cap is **per run**, not per file: files grow without limit across restarts, yet within one run the tail, including user messages and turn ends, is lost. Store merged blocks instead of raw deltas (roughly a hundred times fewer lines), and never drop control events.
- **Every delta goes to disk.** Replay then reduces tens of thousands of events in the browser with O(n) copies each, and `LoadHistory` sends **all** transcripts of a workspace over Wails IPC in one payload.
- **`Store.Load` changes things while reading.** It merges and cleans `-cont-` files and rewrites `meta.json` paths during a read.
- **Four stores for one fact.** `workspaces` (memory), `recorder.metas` (memory + JSON), SQLite `sessions`/`tasks`, and the `history` JSONL all track task state. They drift. For example, SQLite status is set only on turn end, and closing a card updates none of them.

## 12. Architecture change that fixes most of §6–§8 at once

Right now the backend forwards **raw provider events**, and **three** consumers each rebuild conversation state with their own heuristics: the desktop reducer, the mobile `mergeEvents`, and the backend `Constructor`/handoff text accumulators. Each provider has different delta, cumulative and final semantics, so every consumer gets it slightly wrong.

**Move the reduction into Go.** Each adapter emits canonical *item* events with a stable id:

```
item.started {itemId, kind: text|thinking|tool|edit|todo|question|approval, parentItemId?, turnId}
item.delta   {itemId, textDelta | outputDelta}
item.updated {itemId, status, input, output, diffs}
item.completed {itemId, final payload}
```

- Claude maps `stream_event` content-block index to `itemId`. Codex uses `item.id`. OpenCode uses `part.id` (and diffs cumulative text into deltas).
- One Go reducer keeps the per-thread item list. Persist **items** rather than raw deltas, and send item patches (batched) to desktop and mobile.
- Both UIs become thin renderers keyed by `itemId`: nothing to deduplicate and no "merge if last block is text" guesswork. History replay becomes `load items → render`.
